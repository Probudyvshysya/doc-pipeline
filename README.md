# doc-pipeline

Конвейер обработки документов: извлечение текста, контроль полноты, журнал решений
и сторож, который отличает «данных нет» от «система сломалась».

Это вычищенная часть рабочей системы, которая ежедневно работает на собственном сервере:
по расписанию собирает документы из внешнего источника, разбирает их, считает экономику
и присылает готовый вердикт в Telegram. Система начата в августе 2026 года, за месяц
доведена от первого скрипта до автономной работы по cron; в ней около 150 модулей.
Сюда вынесено то, что показывает подход, без данных и бизнес-логики конкретного заказчика.

Все описанные ниже ошибки найдены и закрыты за этот месяц на живых документах.

## Запуск

```bash
pip install -r requirements.txt
python examples/demo.py
```

Вывод:

```
--- 1. Извлечение текста
   tz.docx        -> текст извлечён

--- 2. Контроль полноты
   НЕ ПРОЧИТАНО: smeta.pdf — PDF без текстового слоя (скан)
   🔴 КРАСНЫЙ: решение принимать нельзя, комплект неполный

--- 3. Журнал решений
   записано решение №1
   средняя ошибка прогноза    0.0

--- 4. Сторож конвейера
   до прогона:    КРАСНЫЙ — успешных прогонов не было ни разу
   после прогона: ЗЕЛЁНЫЙ — прогон 0.0 ч назад, обработано документов: 1
```

## Зачем это написано так

Вся система построена вокруг одной мысли: **отсутствие данных должно падать громко.**
Каждый модуль здесь появился после конкретного случая, когда тишина была принята
за порядок.

### extract.py — извлечение текста

Конвертация «как все», через LibreOffice, молча теряет данные. Потерянные данные
выглядят точно так же, как прочитанные: файл есть, текст есть, решение принято.

| Что нашлось | Чем обернулось |
|---|---|
| LibreOffice теряет таблицы `.docx` | На одном техническом задании дало 712 символов вместо 30 262: всё задание было набрано таблицей 13×3. Система оценила документ по титульному листу |
| Excel не читался вообще | Вызов шёл с фильтром Writer, Calc на нём падает с кодом 1 и файл просто не появляется. Обоснования цен и ведомости объёмов полгода не попадали в разбор |
| Колонтитулы и сноски не отдаёт даже python-docx | В колонтитуле одного документа оказались ФИО и телефон ответственного лица, в сносках — размер штрафа, которого не было в основном тексте |

Поэтому `.docx` и `.xlsx` читаются своим кодом прямо из XML (включая объединённые
ячейки, колонтитулы и сноски), а LibreOffice остаётся только для `.doc`, `.rtf`
и старых `.xls`.

### completeness.py — контроль полноты

«Текст извлечён» и «документ прочитан» — разные вещи. Скан без текстового слоя,
файл больше потолка конвертации, сорванный таймаут, неподдержанный формат — всё это
даёт одинаковый результат: файла с текстом нет.

Реальный случай: техническое задание на 35 страниц было выложено сканом, извлечение
дало 48 байт, и документ получил вывод «требований нет» — по одному лишь проекту
договора.

Поэтому модуль считает не прочитанное, а **непрочитанное, с причиной по каждому файлу**.
Пока список не пуст — красный свет, и решение принимать нельзя.

### watchdog.py — сторож

Автоматика ломается тихо. Однажды ежедневный сбор встал на пять суток, и никто не узнал:
расписание отрабатывало, скрипт стартовал, лог писался, данных на выходе не было.

Две ошибки, на которых сторож переписывался:

1. **Свежесть мерилась по времени изменения базы.** Базу трогают и другие процессы,
   поэтому она «выглядела свежей», пока данные устаревали. Предупреждение опоздало
   на трое суток. Теперь метку пишет только успешно завершившийся проход.
2. **Сторож кричал вхолостую** — дважды в день при работающем конвейере, потому что
   проверял доставку, а сломан был отдельный канал. Тревога, которая приходит всегда,
   через неделю перестаёт читаться.

Отсюда три состояния вместо двух: зелёный, жёлтый («прогон был, данных ноль» — это факт,
а не поломка) и красный.

### journal.py — журнал решений

Система выдаёт рекомендации, человек принимает решения, и цепочка обрывается: нигде
не записано, что было взято, почему и совпал ли прогноз с фактом. Без этого качество
рекомендаций нечем измерить, а ошибки повторяются.

Решение фиксируется в момент принятия, с причиной и прогнозом; позже дописывается факт.
Причина короче 25 символов не принимается: через полгода метка «не подходит» не объяснит
ничего. Сводка показывает среднюю ошибку прогноза — это и есть метрика качества системы.

## Как это писалось

Код написан в паре с ИИ (Claude Code) и доведён до продакшена вручную. Рабочий цикл:
поставить задачу, получить черновик, **проверить, что он действительно работает,
а не выглядит правдоподобно**, отладить на реальных данных, зафиксировать найденную
ошибку в докстринге, чтобы она не повторилась.

Все случаи в таблицах выше — не гипотезы, а реально пойманные ошибки. Большинство из них
модель не нашла бы сама: она честно генерировала работающий на вид код, а проблема
вскрывалась только на живых документах.

Свежий пример того же класса: система сделала вывод по заданию, сверившись с его текстом,
но не открыв норматив, на который задание ссылалось. Норматив к тому моменту был заменён
новым, с другими требованиями — вывод оказался неверным. Ошибка найдена до того, как
привела к убытку; в систему добавлено правило: если документ ссылается на норматив,
норматив открывается и читается целиком.

## Состав

```
pipeline/
  config.py        пути и настройки, всё машинозависимое только здесь
  extract.py       .docx, .xlsx, .xls, .doc, .rtf -> текст
  completeness.py  какие документы НЕ попали в текст и почему
  watchdog.py      жив ли конвейер: зелёный / жёлтый / красный
  journal.py       решения с причиной, сверка прогноза с фактом
examples/
  demo.py          прогон всего конвейера на тестовом комплекте
```

## Требования

Python 3.10+, `python-docx`, `openpyxl`, `pdfplumber`. LibreOffice — только для старых
форматов `.doc` и `.rtf`.
